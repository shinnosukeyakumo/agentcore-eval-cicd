# 検証計画

「GitHub Actions で AgentCore Evaluations を回すと、dev → stg の昇格を品質で止められるか」を確かめる。
作って動いたことの確認では終わらせない。わざと劣化させた変更を流し、ゲートが止められるかを測る。

## 問い

1. 劣化したエージェントを、ゲートは stg へ上げずに止められるか
2. 何も変えていないエージェントを、ゲートは誤って止めないか（判定の揺れ）
3. 1 回のゲートにかかる時間と費用は、昇格のたびに回して許容できるか

## 失敗のコスト

| 失敗 | 起きること | 気づけるか |
|---|---|---|
| 劣化を見逃す | 壊れたエージェントが stg に上がる | 気づきにくい。ゲートが緑なので誰も疑わない |
| 誤って止める | 正しい変更が止まり、再実行が繰り返される | 気づける。ただしゲートが信用されなくなる |

見逃しのほうが重い。測定の中心は見逃しに置く。

## 仕込む劣化

| ID | 変更 | 影響する問い |
|---|---|---|
| R1 | `calc_shipping` の北海道・沖縄の送料を 1,200 円 → 500 円にする | shipping-remote の 1 問だけ |
| R2 | システムプロンプトから「必ずツールで確かめてから答える」を消す | 全問 |
| R3 | `get_stock` の docstring を「本の価格を調べる」に書き換える | 在庫系の 3 問 |

## 測る前の予測

- R1 は**見逃す**と予測する。8 問中 1 問だけが誤答になり、Correctness の平均は 0.875 前後になる。閾値 0.8 を上回るため通過してしまう。平均で判定する方式の弱点だ
- R2 は止まると予測する。ツールを呼ばずに答える問いが出て、TrajectoryInOrderMatch と Correctness が落ちる
- R3 は ToolSelectionAccuracy が落ちて止まると予測する。ただしモデルが書名から在庫確認だと推測して、正しく呼べてしまう可能性もある
- 無変更のまま 3 回回すと、LLM 判定の評価器の平均は ±0.05 程度揺れると予測する。TrajectoryInOrderMatch はプログラム判定なので揺れない

## 合格ライン（測る前に宣言する）

- R2 と R3 をゲートが止めること
- 無変更の 3 回で、一度も誤って止めないこと
- ゲート 1 回が 15 分以内に終わること

R1 を見逃した場合は、「問いごとの最低点」や「重要な問いは 1 問でも落ちたら不合格」といった判定方式を追加で検討する。

## 記録するもの

- 各回の評価器別の平均、問いごとの点（`eval/results/raw.json` を Actions の artifact に保存する）
- ゲートの所要時間（Actions の実行時間）
- 費用（Evaluations の入出力トークン。CloudWatch の料金は別）
