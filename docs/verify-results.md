## 分かったこと

### 1. 平均で判定すると、1 問だけの誤答は通る

R1 は「北海道に送ると送料はいくらか」という 1 問だけを壊した。Correctness は 3 回とも 0 だったが、24 件中 3 件の失点では平均 0.875 となり、閾値 0.8 を超えた。業務上は致命的な誤り（送料を 700 円少なく案内する）でも、平均には埋もれる。

### 2. GoalSuccessRate は「答えの正しさ」を見ていない

- R1 の誤答（送料 500 円）を、3 回とも満点にした
- 範囲外の問い（ポイントカード）に正しく「分かりかねます」と答えた回答を、多くの回で 0 点にした。全 6 回・18 試行のうち 14 回が 0 点

この評価器は「ユーザーの目的が果たされたように見えるか」を測る。正しく断ることは減点し、もっともらしい誤答は加点しうる。範囲外の問いを含むデータセットでは、点数がこの問いの揺れに支配される（0.88〜0.96 の揺れの主因）。

### 3. スパンの取り込み遅れが、誤った不合格を生む

Evaluate API は、スパンが揃う前に呼ぶと 2 種類の ValidationException を返した。

- `Provided input contains N log event(s) but no span documents`（ログイベントだけ先に届いた）
- `Provided input has no spans to evaluate`（スパンの一部だけ届いた）

当初はこれを例外として落としていたため、R2・R3 の初回は「劣化を止めた」ように見えた。実際は採点できていなかっただけだ。修正後も、R2 の回で 1 セッションが 10 分待っても揃わず、未完了として不合格になった。

### 4. 仕込んだ劣化が表に出ないことがある

R2（プロンプトの指示削除）と R3（ツール説明の改変）は、Haiku 4.5 の振る舞いを変えなかった。ツールの名前・引数・戻り値から正しく推測していた。「コードを壊したのに点が下がらない」場合は、ゲートの見逃しではなく、エージェントが壊れていない可能性がある。劣化の実験は、回答が実際に変わったことを確かめてから評価する。

## 次に試すこと

1. **問いごとの最低ラインを足す**。重要な問い（送料・在庫）は、1 試行でも Correctness が 0 なら不合格にする。R1 で効果を確かめる
2. **範囲外の問いを GoalSuccessRate の対象から外す**。代わりに Refusal 評価器、または「分かりかねます」を含むかのプログラム判定で見る
3. **取り込み遅れの扱いを分ける**。「点が低い」と「採点できなかった」を別の結果として出し、後者は該当セッションだけ再投入する
4. **劣化を強める**。ツールを 1 つ外す、モデルを小さくする、など振る舞いが確実に変わるもので R2・R3 をやり直す

# 2 巡目: リリースブランチ＋rc Runtime（2026-10-09）

1 巡目の結果を受けて、方針を次のように変えた。

- dev のある時点を `release/<名前>` として切り出し、`release/* → stg` の PR で評価する
- 評価は常設の rc Runtime に、リリース候補のイメージを差し替えて行う（`eval/deploy_rc.py`、UpdateAgentRuntime。CDK は使わない）
- 判定に 3 点を足した
  - 重要な問い（`critical`）は、1 試行でも Correctness が 1.0 未満なら不合格
  - 範囲外の問いは GoalSuccessRate の対象から外す
  - 採点できなかったセッションは 1 度だけ新しいセッションで投げ直し、それでも欠ければ「採点不能」（終了コード 2）として不合格と分ける

## 結果一覧

| # | 実験 | 期待 | 結果 | 所要（eval-gate） |
|---|---|---|---|---:|
| V1 | 送料 1 問の誤り（1 巡目の R1 と同じ） | 不合格 | ❌ 不合格。shipping-remote が 3 試行とも Correctness 0 で、重要問いの最低ラインに掛かった | 4分57秒 |
| V2 | 正常なリリース → マージ → 手動で stg | 合格し、stg に同じイメージが載る | ✅ 合格。dev と stg の ECR の digest が一致（`sha256:7288f3…`） | 4分52秒 |
| V3 | V2 のリリース PR を開いたまま dev に push | 評価が走り直さない | ✅ PR #23 の eval-gate は 1 回だけ。dev 側のデプロイは別に走った | - |
| V4 | dev から stg へ直接 PR | 評価に入る前に失敗し、マージ不可 | ✅ 最初の確認ステップで失敗し、PR は BLOCKED | - |
| V5 | 送料ツールをエージェントから外す | 不合格 | ❌ 不合格。Correctness 0.62、Trajectory 0.57、送料の 3 問が全試行で重要問いの最低ラインに掛かった | 13分18秒 |
| V6 | 正常なリリース（rc を V5 の版から戻す） | 合格 | ✅ 合格。rc は version 4 → 5 へ 11 秒で差し替わった | 4分22秒 |

GoalSuccessRate は、範囲外の問いを外したことで 1.00 に安定した（1 巡目は 0.88〜0.96 で揺れていた）。

## 2 巡目で見つけて直した不具合

| 不具合 | 起きたこと | 対処 |
|---|---|---|
| 必須チェックの素通り | eval-gate のジョブに `if:` を付けていた。条件外の PR ではジョブが skipped になり、GitHub の必須チェックは skipped を合格扱いする。dev から stg へ直接 PR を出すと評価なしでマージできた | `if:` をやめ、最初のステップで release/* 以外を明示的に失敗させる（V4 で確認） |
| 採点待ちが終わらない | ツールを外した問いでは、エージェントがツールを 1 回も呼ばない。ツール系の評価器は結果を返さないのに、完了条件に含めていたため、10 分待って投げ直すまで終わらなかった（初回の V5 は 23分54秒） | ツール系を完了条件から外す。呼ばないこと自体は Trajectory の評価器で拾う |
| rc の差し替え完了の早合点 | UpdateAgentRuntime の直後は status が READY のまま返ることがあり、更新前の版を評価する余地があった | version が上がって READY になるまで待つ（V6 で確認） |

## 残る注意点

- **スパンの取り込み遅れは消えていない**。V5 の再実行では 1 セッションだけ 4〜5 分遅れ、ゲートが 13 分かかった。結果は正しく出るが、所要時間はぶれる
- **rc Runtime は 1 つなので、評価は同時に 1 件ずつ**。GitHub の concurrency は、同じグループに待機中の実行があると古いほうを取り消す。リリース PR が同時に 3 つ以上あると、真ん中の評価が「取り消し」になり再実行が要る。リリースは 1 本ずつ流す運用を前提にする
- **rc スタックの CloudFormation 上のイメージタグは古いまま**になる。rc を `cdk deploy` し直すと、初回のタグに戻る
- 1 アカウントでの再現なので、評価用ロールが rc 以外に触れないことは IAM ポリシーで絞っているだけだ。実案件では rc を dev アカウントに置くことで、アカウント境界でも守られる
