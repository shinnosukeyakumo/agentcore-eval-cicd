## 分かったこと

### 1. 平均で判定すると、1 問だけの誤答は通る

R1 は「北海道に送ると送料はいくらか」という 1 問だけを壊した。Correctness は 3 回とも 0 だったが、24 件中 3 件の失点では平均 0.875 となり、閾値 0.8 を超えた。業務上は致命的な誤り（送料を 700 円少なく案内する）でも、平均には埋もれる。

### 2. GoalSuccessRate は「答えの正しさ」を見ていない

- R1 の誤答（送料 500 円）を、3 回とも満点にした
- 範囲外の問い（ポイントカード）に正しく「分かりかねます」と答えた回答を、多くの回で 0 点にした。全 6 回・18 試行のうち 14 回が 0 点

この評価器は「ユーザーの目的が果たされたように見えるか」を測る。正しく断ることは減点し、もっともらしい誤答は加点しうる。範囲外の問いを含むデータセットでは、点数がこの問いの揺れに支配される（0.88〜0.96 の揺れの主因）。

### 3. スパンの取り込み遅れが、誤った不合格を生む

Evaluate API は、スパンが揃う前に呼ぶと 2 種類の ValidationException を返した。

- `Provided input contains N log event(s) but no span documents`（ログイベントだけ先に届いた）
- `Provided input has no spans to evaluate`（スパンの一部だけ届いた）

当初はこれを例外として落としていたため、R2・R3 の初回は「劣化を止めた」ように見えた。実際は採点できていなかっただけだ。修正後も、R2 の回で 1 セッションが 10 分待っても揃わず、未完了として不合格になった。

### 4. 仕込んだ劣化が表に出ないことがある

R2（プロンプトの指示削除）と R3（ツール説明の改変）は、Haiku 4.5 の振る舞いを変えなかった。ツールの名前・引数・戻り値から正しく推測していた。「コードを壊したのに点が下がらない」場合は、ゲートの見逃しではなく、エージェントが壊れていない可能性がある。劣化の実験は、回答が実際に変わったことを確かめてから評価する。

## 次に試すこと

1. **問いごとの最低ラインを足す**。重要な問い（送料・在庫）は、1 試行でも Correctness が 0 なら不合格にする。R1 で効果を確かめる
2. **範囲外の問いを GoalSuccessRate の対象から外す**。代わりに Refusal 評価器、または「分かりかねます」を含むかのプログラム判定で見る
3. **取り込み遅れの扱いを分ける**。「点が低い」と「採点できなかった」を別の結果として出し、後者は該当セッションだけ再投入する
4. **劣化を強める**。ツールを 1 つ外す、モデルを小さくする、など振る舞いが確実に変わるもので R2・R3 をやり直す

## 観測した所要時間

- deploy-dev（テスト込み）: 1分20秒〜3分
- eval-gate: 3分53秒〜12分18秒（取り込み待ちが長引くと伸びる）
- 深夜帯は、PR 作成から ci のジョブ開始まで 15 分前後待たされる回が多かった（GitHub 側のキュー待ちとみられる。原因は未確認）

# 2 巡目: リリースブランチ＋rc Runtime（2026-10-09）

1 巡目の結果を受けて、方針を次のように変えた。

- dev のある時点を `release/<名前>` として切り出し、`release/* → stg` の PR で評価する
- 評価は常設の rc Runtime に、リリース候補のイメージを差し替えて行う（`eval/deploy_rc.py`、UpdateAgentRuntime。CDK は使わない）
- 判定に 3 点を足した
  - 重要な問い（`critical`）は、1 試行でも Correctness が 1.0 未満なら不合格
  - 範囲外の問いは GoalSuccessRate の対象から外す
  - 採点できなかったセッションは 1 度だけ新しいセッションで投げ直し、それでも欠ければ「採点不能」（終了コード 2）として不合格と分ける

## 結果一覧

| # | 実験 | 期待 | 結果 | 所要（eval-gate） |
|---|---|---|---|---:|
| V1 | 送料 1 問の誤り（1 巡目の R1 と同じ） | 不合格 | ❌ 不合格。shipping-remote が 3 試行とも Correctness 0 で、重要問いの最低ラインに掛かった | 4分57秒 |
| V2 | 正常なリリース → マージ → 手動で stg | 合格し、stg に同じイメージが載る | ✅ 合格。dev と stg の ECR の digest が一致（`sha256:7288f3…`） | 4分52秒 |
| V3 | V2 のリリース PR を開いたまま dev に push | 評価が走り直さない | ✅ PR #23 の eval-gate は 1 回だけ。dev 側のデプロイは別に走った | - |
| V4 | dev から stg へ直接 PR | 評価に入る前に失敗し、マージ不可 | ✅ 最初の確認ステップで失敗し、PR は BLOCKED | - |
| V5 | 送料ツールをエージェントから外す | 不合格 | ❌ 不合格。Correctness 0.62、Trajectory 0.57、送料の 3 問が全試行で重要問いの最低ラインに掛かった | 13分18秒 |
| V6 | 正常なリリース（rc を V5 の版から戻す） | 合格 | ✅ 合格。rc は version 4 → 5 へ 11 秒で差し替わった | 4分22秒 |

GoalSuccessRate は、範囲外の問いを外したことで 1.00 に安定した（1 巡目は 0.88〜0.96 で揺れていた）。

## 2 巡目で見つけて直した不具合

| 不具合 | 起きたこと | 対処 |
|---|---|---|
| 必須チェックの素通り | eval-gate のジョブに `if:` を付けていた。条件外の PR ではジョブが skipped になり、GitHub の必須チェックは skipped を合格扱いする。dev から stg へ直接 PR を出すと評価なしでマージできた | `if:` をやめ、最初のステップで release/* 以外を明示的に失敗させる（V4 で確認） |
| 採点待ちが終わらない | ツールを外した問いでは、エージェントがツールを 1 回も呼ばない。ツール系の評価器は結果を返さないのに、完了条件に含めていたため、10 分待って投げ直すまで終わらなかった（初回の V5 は 23分54秒） | ツール系を完了条件から外す。呼ばないこと自体は Trajectory の評価器で拾う |
| rc の差し替え完了の早合点 | UpdateAgentRuntime の直後は status が READY のまま返ることがあり、更新前の版を評価する余地があった | version が上がって READY になるまで待つ（V6 で確認） |

## 残る注意点

- **スパンの取り込み遅れは消えていない**。V5 の再実行では 1 セッションだけ 4〜5 分遅れ、ゲートが 13 分かかった。結果は正しく出るが、所要時間はぶれる
- **rc Runtime は 1 つなので、評価は同時に 1 件ずつ**。GitHub の concurrency は、同じグループに待機中の実行があると古いほうを取り消す。リリース PR が同時に 3 つ以上あると、真ん中の評価が「取り消し」になり再実行が要る。リリースは 1 本ずつ流す運用を前提にする
- **rc スタックの CloudFormation 上のイメージタグは古いまま**になる。rc を `cdk deploy` し直すと、初回のタグに戻る
- 1 アカウントでの再現なので、評価用ロールが rc 以外に触れないことは IAM ポリシーで絞っているだけだ。実案件では rc を dev アカウントに置くことで、アカウント境界でも守られる

# 3 巡目: dev と stg を別アカウントに分ける（2026-10-17）

1・2 巡目は 1 アカウントの中で ECR・Runtime・ロールを分けて真似ていた。3 巡目では stg 用に別の AWS アカウントを用意し、実際にアカウントをまたいで昇格させた。

## 構成の変更

| | dev アカウント | stg アカウント |
|---|---|---|
| 土台のスタック | `AgentCoreEvalCicd-Bootstrap`（OIDC、dev の ECR、dev デプロイ用ロール、評価用ロール） | `AgentCoreEvalCicd-StgBootstrap`（OIDC、stg の ECR、stg デプロイ用ロール） |
| Runtime | dev、rc（評価用） | stg |
| ECR の読み取り許可 | dev の ECR のリポジトリポリシーで、stg デプロイ用ロールにだけ読み取り 4 操作を許可 | stg デプロイ用ロールの IAM ポリシーで、dev の ECR の読み取りを許可 |

- 評価用ロールは dev アカウントにしかないので、stg には構造上触れられない
- アカウント ID はコードに書かず、土台のデプロイ時に `-c devAccount=... -c stgAccount=...` で渡す
- リポジトリポリシーは相手のロールを ARN で名指しするので、stg の土台を先にデプロイした
- `deploy-stg.yml` は両方の ECR にログインし（`amazon-ecr-login` の `registries` に 2 アカウントを渡す）、`crane copy` でアカウントをまたいでコピーする。複数レジストリにログインすると `registry` 出力が空になるので、ホスト名はアカウント ID から組み立てる

## 結果

| 段 | 結果 |
|---|---|
| release/20261017-acct → stg の PR（dev アカウントの rc で評価） | 合格（6分18秒） |
| dev の ECR → stg の ECR へのコピー | 成功。両アカウントの digest が `sha256:7288f3…` で一致 |
| stg アカウントへの cdk deploy | 成功 |
| 疎通確認 | 1 回目は失敗（下記）。Anthropic の利用目的の申請後に再実行して成功（1分44秒） |

## 新しいアカウントで踏んだこと

| 事象 | 内容 |
|---|---|
| アカウントの確認待ち | 作成直後の Bedrock は `Your account is currently being verified` で拒否された。CloudFormation・ECR・AgentCore の API は確認中でも動いた |
| Anthropic の利用目的の申請 | 未提出のまま一度だけ Converse が通ったが、約 1 時間後には Runtime からも手元からも `Model use case details have not been submitted for this account` で拒否された。申請は必須。申請後は `agreementAvailability` が `NOT_AVAILABLE` から `AVAILABLE` に変わり、すぐ呼べた |
| 疎通確認の失敗の見え方 | ワークフロー側には `Received error (500) from runtime` としか出ない。原因は stg アカウントの Runtime のロググループに出ていた |

## 評価で見つかったこと

PR #30 の評価で、TrajectoryInOrderMatch が 0.90 だった。中身は shipping-free の 2 試行で、エージェントは送料計算のツールを呼ばずに「東京都への配送は送料無料のため 3,080 円」と答えていた。金額は正しいが理由が違う（正しくは小計が 3,000 円以上だから無料）。

| 評価器 | この回答への点 |
|---|---|
| Correctness | 1.0（核心の金額が合っている） |
| GoalSuccessRate | 0 |
| TrajectoryInOrderMatch | 0（ツールを呼んでいない） |

重要な問いの最低ラインは Correctness にしか掛けていないので、ゲートは通った。推測で当たった答えは Correctness では見抜けず、軌跡の評価器でしか拾えない。重要な問いには、Trajectory にも最低ラインを掛けるかを検討する余地がある。

# 4 巡目: 残りの論点を確かめる（2026-10-17〜18）

## 費用の実績

Cost Explorer（2026-10-08〜17、すべて Estimated）の表示。

|---|---|---|

## 無変更での再実行と、Trajectory の最低ライン

重要な問いの最低ラインに `Builtin.TrajectoryInOrderMatch` を足した（3 巡目で、ツールを呼ばずに推測で当たった答えを Correctness が満点にしたため）。

### 1 回目の 5 回（予測: 2〜3 回が不合格）

正常な版（`cc195c2…`）を 5 回評価したところ、**4 回が不合格**になった。落ちたのはすべて Trajectory だったが、調べると原因はエージェントではなかった。

- 落ちた試行の回答には、ISBN や在庫数など、ツールを呼ばなければ分からない値が正しく入っていた
- 評価器の説明は `Actual: []`（ツール呼び出しが 1 つも見えていない）
- 同じセッションを後から採点し直すと、ツール呼び出しが見つかり Trajectory は 1.0 になった

**ツールのスパンが届く前に採点していた。** 2 巡目で、ツールを呼ばないセッションで採点待ちが終わらない不具合を直すため、ツール系の評価器を完了待ちの条件から外していた。それで、ツールのスパンを待たずに Trajectory を採点していた。

### 対処

重要な問いで最低ラインを下回った試行だけ、90 秒待って採点し直し、後の結果を採る。採点し直しが空振りした場合は元の結果を残す（不合格を見逃さないため）。

### 2 回目の 5 回（予測: 5 回とも合格）

| 回 | 判定 | 所要 | 備考 |
|---|---|---|---|
| 1 | 合格 | 3分42秒 | |
| 2 | 合格 | 3分21秒 | |
| 3 | 合格 | 13分09秒 | 1 セッションのスパンが揃わず、新しいセッションで投げ直した |
| 4 | 合格 | 3分28秒 | |
| 5 | 合格 | 3分39秒 | |

5 回とも全評価器が 1.00。ただし、この 5 回では Trajectory の取りこぼしがたまたま起きなかったので、採点し直しが正常な版を救う場面は実地では見ていない。

送料ツールを外した版（V5 と同じイメージ）を同じ判定で評価すると不合格だった。最低ラインを下回った 9 件は、採点し直しても 0 のままだった。

## stg の承認者

stg の Environment に承認者（リポジトリの持ち主）を付けた。

- 手動で deploy-stg を起動すると、実行は `waiting` で止まる。この時点では AWS の認証すら走らない
- 承認すると先に進み、デプロイが成功した
- 承認者・状態・コメントが実行の記録に残る

## オンライン評価（prd の監視の代わりに stg で確かめた）

stg の Runtime に `OnlineEvaluationConfig` を付けた。正解データは渡せないので、正解なしで使える評価器を選んだ。

| 設定 | 値 |
|---|---|
| 評価器 | Correctness、Faithfulness、ToolSelectionAccuracy、Refusal |
| サンプリング | 100%（検証のため。実運用では下げる） |
| セッションのタイムアウト | 2 分 |
| 前提 | stg アカウントで Transaction Search を有効にした（送り先が既定の XRay だった） |

8 問を 1 回ずつ流したところ、**562 秒後（約 9 分）に 8 件分の結果がまとめて出た**。Correctness・Faithfulness・ToolSelectionAccuracy はすべて 1.0、Refusal はすべて 0。範囲外の問いに「分かりかねます」と答えた回答も Refusal は 0（拒否とみなさない）だった。

### つまずいたこと

- CDK の `OnlineEvaluationConfig` は、型定義の説明では `executionStatus` の既定が `ENABLED` だが、指定しないと `DISABLED` で作られた（aws-cdk-lib 2.272.0）。`ExecutionStatus.ENABLED` を明示して直した。詳細は [oss-findings.md](oss-findings.md)
- stg の `aws login` 形式のプロファイルを Python（boto3）から使うには `botocore[crt]` が要る。`aws configure export-credentials --format env` で一時的な認証情報を書き出して回避した

## 手動確認との比較

人が手で確かめる時間は測れていない（人が実際にやる必要があるため）。測れたのはエージェントの応答時間だけ。

| 項目 | 値 |
|---|---|
| 8 問を 1 回ずつ投げたときの応答時間の合計（dev の Runtime） | 58 秒 |
| 回答の文字数の合計 | 890 字 |
| 比べる相手のゲート | 24 セッション（8 問 × 3 回）を人の手なしで 4〜5 分 |

人が確かめる場合は、この待ち時間に加えて、890 字の回答を読み 8 つの正解と見比べる時間がかかる。`eval/manual_check.py` を人が一度流せば測れる。
