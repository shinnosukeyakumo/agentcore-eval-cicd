## 分かったこと

### 1. 平均で判定すると、1 問だけの誤答は通る

R1 は「北海道に送ると送料はいくらか」という 1 問だけを壊した。Correctness は 3 回とも 0 だったが、24 件中 3 件の失点では平均 0.875 となり、閾値 0.8 を超えた。業務上は致命的な誤り（送料を 700 円少なく案内する）でも、平均には埋もれる。

### 2. GoalSuccessRate は「答えの正しさ」を見ていない

- R1 の誤答（送料 500 円）を、3 回とも満点にした
- 範囲外の問い（ポイントカード）に正しく「分かりかねます」と答えた回答を、多くの回で 0 点にした。全 6 回・18 試行のうち 14 回が 0 点

この評価器は「ユーザーの目的が果たされたように見えるか」を測る。正しく断ることは減点し、もっともらしい誤答は加点しうる。範囲外の問いを含むデータセットでは、点数がこの問いの揺れに支配される（0.88〜0.96 の揺れの主因）。

### 3. スパンの取り込み遅れが、誤った不合格を生む

Evaluate API は、スパンが揃う前に呼ぶと 2 種類の ValidationException を返した。

- `Provided input contains N log event(s) but no span documents`（ログイベントだけ先に届いた）
- `Provided input has no spans to evaluate`（スパンの一部だけ届いた）

当初はこれを例外として落としていたため、R2・R3 の初回は「劣化を止めた」ように見えた。実際は採点できていなかっただけだ。修正後も、R2 の回で 1 セッションが 10 分待っても揃わず、未完了として不合格になった。

### 4. 仕込んだ劣化が表に出ないことがある

R2（プロンプトの指示削除）と R3（ツール説明の改変）は、Haiku 4.5 の振る舞いを変えなかった。ツールの名前・引数・戻り値から正しく推測していた。「コードを壊したのに点が下がらない」場合は、ゲートの見逃しではなく、エージェントが壊れていない可能性がある。劣化の実験は、回答が実際に変わったことを確かめてから評価する。

## 次に試すこと

1. **問いごとの最低ラインを足す**。重要な問い（送料・在庫）は、1 試行でも Correctness が 0 なら不合格にする。R1 で効果を確かめる
2. **範囲外の問いを GoalSuccessRate の対象から外す**。代わりに Refusal 評価器、または「分かりかねます」を含むかのプログラム判定で見る
3. **取り込み遅れの扱いを分ける**。「点が低い」と「採点できなかった」を別の結果として出し、後者は該当セッションだけ再投入する
4. **劣化を強める**。ツールを 1 つ外す、モデルを小さくする、など振る舞いが確実に変わるもので R2・R3 をやり直す
